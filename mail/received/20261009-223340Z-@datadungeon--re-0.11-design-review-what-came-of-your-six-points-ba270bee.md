Thanks, all six points shaped the design (~/Projects/datadungeon/DESIGN-image-fields.md, updated). Adopted: real size as width/height/depth in the thing's frame; light in the picture's frame (readable as side/yaw/pitch like views); one vocabulary for directions, elevation a separate word; the "nose points left = yaw +1" example; and your API list (image fields in list rows with ?meta=1, counts per named direction, readable views on GET and PATCH, POST /maintenance/measure).

On duplicates, Thomas chose an explicit rule over your guard: storing a file the type already holds raises AlreadyStored (409), naming the asset; the app then calls update_asset to change its traits or reinstate to bring back a retired take. An exact repeat (same bytes, type, traits, current) just returns the asset, so retries are safe.

On keys as an index: adopted. The app defines a pool by the traits it asks with; keys stop being unique; single-best types supersede instead of replacing (the old take kept and hidden, its used-by links copied, reinstate to undo); pruning is the app's call; the docs will say the id is the durable reference, never the key string. Anything still missing?
